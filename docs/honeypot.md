# Honey-pot

Separate opt-in cog. Defaults: enabled, real bans once the current bot-authored warning exists and safety checks pass. The testing bot/guild can also ban, only with APBOT_DATABASE_NAME=ap-test. Production requires ap-students (or the default). Unknown bot/guild identities are ignored. No new dependencies or config.json keys.

1. Create a text channel named `honey-pot`. Make it readable and writable by the intended members; disable unnecessary features such as creating threads. Do not encourage people to post there.
2. Create a private text channel named `honey-pot-log`. Deny View Channel to @everyone and ordinary roles. Allow staff and APBot. Bot Staff and Senior Bot Staff are allowed to read logs but this alone does not exempt them from the trap. Bot requires View Channel, Send Messages, Embed Links and Attach Files in the log. In the trap it needs View Channel, Send Messages, Read Message History and Manage Messages. Grant Ban Members at guild level for enforcement; bot role must be above target members.
3. Start the bot. It will find the matching warning in the last 50 messages or post a new one. Pinning is optional. Keep the warning visible (channel topic is recommended as well). The bot remembers the warning ID and rechecks it before a ban; if the warning is deleted or changed, enforcement stops until a valid warning is found or the bot is restarted. If channels are created after startup, restart to create the warning. Remove obsolete notices manually.
4. Test with a non-staff account: text, attachment-only, reply, normal channel, repeated messages. Use a disposable non-staff test account: enforcement really bans it. To test without punishment, optionally set HONEYPOT_DRY_RUN=True and restart. Admin and moderator messages are always ignored.
5. Production: real bans are enabled by default when the current warning exists. Do not enable until staff approve the policy and the channel is clearly marked. Set `HONEYPOT_ENABLED = False` and restart for emergency stop; requests already sent to Discord cannot be undone.

Enforcement: exact channel name, configured bot/guild, current bot-authored warning older than trigger, fresh member and message, private log and successful initial log send, role hierarchy. Requires message-content intent. Ban reason `Talking in honeypot`; zero historical message purge. After confirmed ban, record existing `ban` infraction via DB, delete only trigger, attempt DM matching the existing /ban embed and appeal field. DM and DB failures do not roll back the confirmed Discord ban and are noted in terminal logs. Appeal policy is unchanged; current production review period is 14 days. No mute or points. Original uploaded files are copied to the private log in separate messages above the moderation embed (no forced spoilers). Original text is in the embed, with a full text file if longer than 800 characters or containing backticks. Sticker, embed, poll and forwarded-message metadata are archived where available; external linked images and forwarded attachments are not downloaded. Max 10 attachments, 8 MiB each (or guild upload limit if lower), 24 MiB total, 60 seconds for evidence. Evidence upload failure prevents a ban; partial uploads may remain; attachment filenames include the original message ID. Log groups are serialized; links in the embed identify each evidence message. The log retains the original message ID without a dead jump link; individual file links point to the archived evidence. Max four concurrent users; overload is logged and skipped. Successful bans are deduplicated for two minutes; old messages and departed members are skipped. A role named Bot Staff is not itself punishment immunity. Discord lacks atomic conditional bans, so rechecks reduce but cannot eliminate races. If the trigger is deleted before fetch, the recent gateway event still counts; other fetch failures stop enforcement. This avoids competition with the scam detector. No guarantee against spam in DMs, threads or unrelated channels. No persistent queue/retry of failed bans.

Tests use an isolated Nextcord stub, not live Discord. Run `python -m pytest tests/test_honeypot.py -q`. Review real gateway behavior and permissions before production enforcement. The test bot can perform actual bans in the test guild with the test database environment. The warning describes the production appeal window; test appeal timers are separately configured.
